### Gate Details

#### Type safety — PASS
Kotlin jest statycznie typowany z natury; brak opcjonalności dla typów bez explicite `?`. Modele domenowe (`Cap`, `CapExtended`, `Country` itp.) to `data class` z jawnie typowanymi polami. Serializacja (kotlinx.serialization) wymusza kontrakt typów na granicy API. KSP procesuje Hilt i generuje typebezpieczne klasy DI.

Dowód: `app/build.gradle` linia 3 (`id 'org.jetbrains.kotlin.android'`), Kotlin language spec; `model/Cap.kt` — `@Serializable data class Cap(val id: Int, val name: String, ...)`.

#### Convention-based — PARTIAL (~)
Android/Jetpack ma silnie ugruntowane konwencje ekosystemowe (Google Architecture Guides), a projekt ich przestrzega:
- Jedna aktywność (`MainActivity`) + nawigacja Compose
- ViewModel per ekran, Repository per domena danych
- PagingSource per stronnicowany widok
- `di/` dla modułów Hilt
- `ui/<feature>/<Feature>Screen.kt` + `<Feature>ViewModel.kt`

Jednak te konwencje są *sugerowane przez ekosystem*, nie *wymuszane przez framework* — inaczej niż Spring Boot (autoconfiguration) czy Rails (convention over configuration). Dwie konkretne luki:

1. **Niespójność modeli**: `data/model/Country.kt` jest w pakiecie warstwy danych, ale wszystkie modele Cap (Cap, CapExtended, Liner, Producer itp.) siedzą w top-level `model/`. Brak dokumentacji reguły podziału.
2. **Brak pliku instrukcji**: żaden z plików `CLAUDE.md`/`AGENTS.md` nie dokumentuje konwencji projektu dla agenta.

Dowód: glob źródeł — `app/src/main/java/pl/sroki/cci/android/` — widoczna niespójność; brak CLAUDE.md potwierdzony globem.

```markdown
## Architektura projektu

### Struktura pakietów
Korzeń: `app/src/main/java/pl/sroki/cci/android/`

```
data/
  datasource/remote/    ← Interfejsy Retrofit (ApiService)
  model/                ← Modele używane TYLKO w warstwie danych (np. Country)
di/                     ← Moduły Hilt (@Module @InstallIn)
model/                  ← Modele domenowe współdzielone (Cap, CapExtended, itp.)
                          oznaczone @Serializable jeśli serializowane przez API
navigation/             ← Definicje tras (Screen.kt — sealed class / object)
ui/
  <feature>/            ← Jeden folder per funkcja
    <Feature>Screen.kt  ← Composable entry point ekranu
    <Feature>ViewModel.kt ← ViewModel ekranu (@HiltViewModel)
    <Feature>*View.kt   ← Composable pod-komponenty danego ekranu
  components/           ← Współdzielone, reużywalne Composable
  theme/                ← Color.kt, Type.kt, Shape.kt, Theme.kt
CCIApplication.kt       ← @HiltAndroidApp entry point
MainActivity.kt         ← Single-activity, NavHost
```

### Reguła podziału modeli
- `model/` — modele domenowe używane przez wiele ekranów lub warstwę UI
- `data/model/` — modele ściśle wewnętrzne dla warstwy danych
- Nowe modele API domyślnie trafiają do `model/` z adnotacją `@Serializable`

### MVVM + Repository — granice odpowiedzialności
- **Composable** — tylko rendering i propagacja eventów; zero logiki biznesowej
- **ViewModel** — stan UI jako `StateFlow`/`Flow`, ekspozycja przez `collectAsState()`; wywołuje Repository
- **Repository** — koordynuje źródła danych (API remote, lokalna baza); nie zna nic o UI
- **PagingSource** — implementacja `PagingSource<Int, T>`; tworzony przez Repository, nie ViewModel

### Hilt DI — wzorzec wstrzykiwania
- Moduły w `di/`, nazwane `<Domain>Module.kt`
- API serwisy jako `@Singleton` z `NetworkModule`
- Repozytoria wstrzykiwane przez konstruktor do ViewModel (`@HiltViewModel`)
- Nowy ekran: utwórz `@HiltViewModel class <Feature>ViewModel @Inject constructor(...)`

### Nawigacja
- Trasy zdefiniowane w `navigation/Screen.kt` jako `sealed class Screen`
- NavHost w `MainActivity.kt` — dodaj trasy tam
- Nawigacja między ekranami przez `navController.navigate(Screen.X.route)`

### Testowanie
- Testy jednostkowe: `app/src/test/java/pl/sroki/cci/android/`
  - Testuj ViewModel i Repository logic (nie Composables)
  - Mockuj zależności przez constructor injection
- Testy instrumentowane: `app/src/androidTest/java/pl/sroki/cci/android/`
  - Używaj `ComposeTestRule` dla testów UI
  - Preferuj `composeTestRule.onNodeWithText(...)` nad Espresso dla Compose
```
